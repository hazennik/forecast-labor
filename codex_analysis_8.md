# Forecast-Labor Production Readiness Assessment (Phases 1-4 Refresh)

**Scope:** Re-evaluate the `forecast-labor` repo against the Phase 1‑4 promises recorded in `docs/planning/IMPLEMENTATION_STATUS.md`, confirm whether the claimed test/CI gates exist, and document the true readiness gap before any Phase 5+ model work (which the plan still marks as not yet started) begins.

## 1. Documentation & Plan Integrity — Critical Risk
- The status doc simultaneously declares “Phase 4 COMPLETE” with “production-ready” feature engineering (docs/planning/IMPLEMENTATION_STATUS.md:3-10) while the “Current Focus” block still says “🚧 PHASE 3.5: Testing Foundation (CURRENT - BLOCKING)” and even lists “🔴 Phase 4 BLOCKED Until …” (docs/planning/IMPLEMENTATION_STATUS.md:903-942), so stakeholders do not have a single authoritative source of truth.
- The Go/No-Go table claims every gate—including 287/287 tests, determinism, diagnostics, and feature engineering—is ✅ (docs/planning/IMPLEMENTATION_STATUS.md:211-224), yet the same document later marks `tests/etl`, `tests/seasonal`, `tests/validators` as “🚧 In Progress” and `tests/features` as “📋 Planned” (docs/planning/IMPLEMENTATION_STATUS.md:1143-1148). Progress summary rows repeating “Feature Engineering: 100% ✅ (10 components, 100+ tests)” (docs/planning/IMPLEMENTATION_STATUS.md:957-980) therefore cannot be trusted.

## 2. Phase 1 – Infrastructure & Tooling — High Risk
- The health-check script probes MLflow on `http://localhost:5000/health` (scripts/check_infrastructure_health.py:18-38), but docker-compose exposes MLflow on port 5050 (`"5050:5000"`) to avoid macOS conflicts (docker-compose.yml:80-88). Running `python scripts/check_infrastructure_health.py` will always mark MLflow unhealthy even when the container is up, so the advertised “Infrastructure Health ✅” gate is a false positive.
- CI cannot act as a go/no-go gate. The workflow allows Ruff, mypy, integration pytest, and Codecov uploads to fail silently (`continue-on-error: true`), and it only runs tests tagged `unit` via `pytest -m "unit"` (.github/workflows/test.yml:41-84). Most suites—including the feature registry tests—lack any `@pytest.mark.unit` annotations, so they never execute at all (tests/features/test_registry.py:13-200). The integration tests that actually touch ETLs are marked `@pytest.mark.integration` (tests/etl/test_public_etl_pipelines.py:17-214) and are explicitly ignored if they fail, so CI provides no protection despite the plan’s claim that “Phase 1-4 Tests Complete (160+/287 cases)”.

## 3. Phase 2 – Public Data Pipelines — Medium Risk
- `scripts/test_pipelines.py` spins up each ETL, hits the live APIs, and asserts on real network responses for UI Claims, Treasury, CES, LAUS, Weather, Strikes, and CNBFS (scripts/test_pipelines.py:16-215). This contradicts the plan’s statement that “Integration tests for each ETL pipeline … mocked APIs … no external calls in CI” (docs/planning/IMPLEMENTATION_STATUS.md:503-512). CI is therefore flaky/offline-hostile and still lacks deterministic regression coverage.
- Weather ETL still defaults to synthetic fallback data because `ALLOW_FALLBACK_DATA` is `true` unless overridden (etl/public/weather/weather_etl.py:18-103). The status doc advertises that the NOAA pipeline “Implemented Weather API (no longer stub)” with fallback only for local dev (docs/planning/IMPLEMENTATION_STATUS.md:227-236). Operators who trust the doc will unknowingly continue generating fake hurricane impacts in production unless they manually flip two environment variables.

## 4. Phase 3 – Validation & Seasonal — Critical Risk
- The determinism baseline file is only a scaffold: every hash and row/column count is `null`, and the JSON uses a `vintages` key (tests/fixtures/golden_baselines/vintage_hashes.json:1-56). `scripts/verify_vintage_determinism.py` expects a populated baseline under `baseline["sources"]` and will crash or fail immediately (scripts/verify_vintage_determinism.py:205-287). The Go/No-Go row that says “Vintage Determinism ✅” therefore does not reflect reality.
- The seasonal diagnostics “golden” file is also empty—the monitored CES series have every M- and Q-statistic set to `null` (tests/fixtures/golden_baselines/golden_seasonal_diagnostics.json:1-60)—and the CLI only supports `--record`, not the `--verify` flag that CI invokes (scripts/record_golden_diagnostics.py:353-397 vs .github/workflows/test.yml:74-84). Every workflow run attempting to “check golden diagnostics” will exit with an argparse error before looking at any data, so the advertised regression gate does not exist.
- `scripts/run_seasonal_adjustment.py` loads each series through `StorageClient` paths like `vintages/bls_ces/latest/ces.parquet` and `vintages/bls_laus/latest/laus.parquet` (scripts/run_seasonal_adjustment.py:22-62), but BaseETL only ever writes `data/vintages/{source}/{YYYY-MM-DD}/{source}_vintage.parquet` (etl/common/base.py:267-314). Because no job publishes a “latest” alias in MinIO, the seasonal tool cannot read inputs or emit diagnostics despite the status doc’s “Seasonal adjustment ✅ with diagnostics” messaging.

## 5. Phase 4 – Feature Engineering — Critical Risk
- `FeatureBuilder.build_aggregations` insists on a `state` column before calling `StateAggregator` (scripts/build_features.py:326-358), but the LAUS ETL exposes `state_name` and `state_fips` instead (etl/public/bls_laus/laus_etl.py:292-329), and the aggregator itself raises a `ValueError` when the requested column is missing (features/aggregations/state_aggregator.py:57-88). As a result, the “state → national aggregation” path can never run, yet the plan labels it ✅ along with Phase 4 completion.
- The plan touts “Feature Registry … Optional database persistence” as delivered (docs/planning/IMPLEMENTATION_STATUS.md:69-77), but the implementation still logs “database_persistence_not_yet_implemented” and contains only TODO comments (features/registry.py:387-410). Registry entries therefore live purely in-memory, so there is no durable provenance or lineage trail despite the readiness claim.

## 6. Implementation Status Cross-Reference
- Even within the status doc, the coverage matrix still shows every Phase 5 (models/reconciliation) line item, the entire Phase 6 backtesting suite, the Phase 6.5 API work, and all Phase 7 subnet adapters as “📋 Planned” (docs/planning/IMPLEMENTATION_STATUS.md:1055-1101). That matches the repository: `models_src/`, `backtests/`, `subnets/`, and dashboard/agent directories are scaffolds only, so Phase 5+ development truly has not begun.
- Testing rows confirm that the fixtures, ETL suites, and seasonal tests remain “🚧 In Progress” and that Phase 4 feature tests are still “📋 Planned” (docs/planning/IMPLEMENTATION_STATUS.md:1143-1148), which contradicts the Go/No-Go gate but does reinforce that later-phase readiness work is outstanding.

## Readiness Verdict & Recommended Next Steps
- **Verdict:** Forecast-Labor is still not production-ready through Phase 4. CI gates are non-blocking, the determinism and diagnostics baselines are placeholders that prevent their scripts from running, seasonal tooling cannot read from the published vintage layout, and the feature builder’s flagship aggregations crash because the expected columns do not exist. Declaring Phase 4 “complete” masks these blockers, and Phases 5-9 remain unstarted scaffolding.
- **Recommended actions before touching Phase 5 models:**
  1. Fix the CI contract: point the health check at the actual MLflow port, remove `continue-on-error` from lint/type/integration stages, and stop filtering tests with `-m unit` until every suite is correctly marked; otherwise the touted “287/287 green” signal remains fictional.
  2. Populate `tests/fixtures/golden_baselines/` with real hashes and M/Q values using the provided scripts, adjust the determinism JSON structure to match what `verify_vintage_determinism.py` expects, and add a real `--verify` path to `record_golden_diagnostics.py` so those Go/No-Go gates can actually run.
  3. Align seasonal tooling and feature engineering with real data layouts: either publish `vintages/{source}/latest/*.parquet` in MinIO or point the scripts at `data/vintages/{source}/{YYYY-MM-DD}/…`, and change the LAUS aggregation code to consume the `state_name/state_fips` columns the ETL provides.
  4. Keep fallback data disabled by default in Weather ETL, add mocked network fixtures for the pipeline tests, and persist feature-registry metadata (or explicitly scope it to in-memory) so Phase 2–4 commitments match what the code actually does.

Addressing these Phase 1‑4 gaps will make the Implementation Status dashboard trustworthy and unblock the not-yet-started Phases 5‑9 roadmap.
